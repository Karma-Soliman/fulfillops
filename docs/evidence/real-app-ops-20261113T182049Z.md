# Real application Compose persistence evidence

Captured 2026-11-13 (UTC). Compose used `LB_HOST_PORT=18080` because kind owns host port 8080. This is the main Compose project and its PostgreSQL named volume; the project was not torn down with `-v`.

## Before restart

`LB_HOST_PORT=18080 make up` completed with exit code 0. Readiness returned:

```text
HTTP/1.1 200 OK
{"status":"ready"}
```

`POST /api/v1/orders` with a unique timestamped `Idempotency-Key` and one `PART-200` returned HTTP 202:

```json
{"order_id":"84ef20bd-f098-4963-9fd1-902f10d7386f","status":"queued"}
```

Before the restart, polling `GET /api/v1/orders/84ef20bd-f098-4963-9fd1-902f10d7386f` returned:

```json
{"order_id":"84ef20bd-f098-4963-9fd1-902f10d7386f","status":"completed","total_cents":599}
```

## Restart and persistence check

Ran `make down` (exit 0; target executes `docker compose down`, without `-v`), then `LB_HOST_PORT=18080 make up` (exit 0). Readiness returned `{"status":"ready"}` on the first poll.

After restarting the application and database containers, the same order still existed and remained completed:

```text
GET /api/v1/orders/84ef20bd-f098-4963-9fd1-902f10d7386f
{"order_id":"84ef20bd-f098-4963-9fd1-902f10d7386f","status":"completed","total_cents":599}
```

The API container identity was:

```text
uid=10001(app) gid=10001(app) groups=10001(app)
```
