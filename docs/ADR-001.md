# ADR-001: Application Architecture and Data Consistency
## 1. Context

FulfillOps is an order-processing application that must accept orders, reserve inventory safely, and process background jobs reliably.

The system must support multiple API instances and workers. It must also handle repeated requests, concurrent stock reservations, worker crashes, and application restarts without creating duplicate orders or overselling inventory.

The architecture therefore needs a shared persistent data store and reliable coordination between application components.

## 2. Decisions

### 2.1 FastAPI for the HTTP API

We chose FastAPI to implement the HTTP API.

It provides request validation, structured responses, and support for health and metrics endpoints. The API is separated into modules for routes, schemas, database access, models, and metrics.

### 2.2 PostgreSQL as the shared database

We chose PostgreSQL as the source of truth for application state.

Orders, order items, inventory, idempotency keys, and background jobs are stored in PostgreSQL. API replicas and workers use the same database rather than relying on process-local state.

This allows multiple instances to coordinate through database transactions and constraints.

### 2.3 SQLAlchemy and Alembic for database management

SQLAlchemy is used for database access and models. Alembic manages version-controlled schema migrations.

Migrations run through a dedicated migration service before the API starts, rather than independently in every API replica.

### 2.4 Transactional inventory reservation

Order creation and inventory reservation happen in a single database transaction.

The API locks the relevant inventory rows before checking and updating available stock. If any operation fails, the transaction rolls back.

This prevents concurrent requests from reserving the same remaining stock.

### 2.5 Database-backed idempotency

Idempotency keys and normalized request payload hashes are stored in PostgreSQL.

A repeated request with the same key and payload returns the original order. Reusing the key with a different payload returns a conflict.

This decision avoids relying on in-memory state, which would not be shared between API replicas and would disappear after a restart.

### 2.6 PostgreSQL-backed background jobs

We chose to store background jobs in PostgreSQL instead of introducing a separate message broker.

Each accepted order has one associated job. Workers claim jobs using database row locking and `SKIP LOCKED`.

Leases and lease tokens support recovery after worker crashes and prevent workers with outdated claims from finalizing jobs.

Retries are bounded, with backoff between attempts.

### 2.7 Nginx and multiple application instances

Nginx distributes incoming HTTP requests across API replicas.

The Compose configuration runs two API replicas and two worker replicas. Since application state is stored in PostgreSQL, the instances can operate against the same data.

### 2.8 Prometheus for observability

Prometheus collects metrics from the API and workers.

The application exposes health endpoints and metrics so that service health, request activity, and worker behaviour can be monitored.

## 3. Alternatives Considered

| Alternative | Reason not selected |
|---|---|
| Process-local storage | Not shared across replicas and lost after restarts |
| In-memory idempotency | Cannot reliably coordinate concurrent API instances |
| Separate message broker | Adds another infrastructure component; PostgreSQL-backed jobs are sufficient for this project's requirements |
| Reserve stock during worker processing | Could allow multiple accepted orders to compete for the same remaining stock |
| Run migrations in every API replica | Could cause concurrent migration attempts |

## 4. Consequences

### Positive consequences

- PostgreSQL provides a shared source of truth.
- Transactions protect order creation and stock reservation.
- Database-backed idempotency supports safe request retries.
- Multiple workers can claim different jobs concurrently.
- Leases and bounded retries support worker crash recovery.
- Version-controlled migrations make schema changes reproducible.
- The architecture avoids introducing a separate message broker.

### Trade-offs and limitations

- PostgreSQL handles both business data and background job coordination.
- Worker polling creates periodic database queries.
- Database availability is important to both API and worker operation.
- A database-backed queue may need reconsideration if future workload or throughput requirements increase.
- Failed orders retain their inventory reservations for operator review rather than being automatically restocked.
